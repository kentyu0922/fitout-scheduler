# PMP Schedule 模块化架构与工序规则 V1

日期：2026-10-09｜用途：中国大陆租户办公／研发装修 L2 总控计划｜状态：专业逻辑规格提案，尚未实施到 3.11.1。

## 一、设计结论

采用“20 套可识别基础组合＋按实际范围加载的专项模块＋项目条件调整”。20 套组合复用同一套核心工序和采购模块；行业差异体现为需求、设计输入、风险筛查及业务接管条件，不凭行业名自动增加设备或设施。

每套组合可以单独展示和验收；底层工序只维护一份。行业模块不是换标题；Add-on 也不是追加一段孤立甘特条，而是把专项需求、设计、采购、安装、调试和交付接口分别接入项目全过程。

本规格为 PM 工序设计建议。引用的法规只支持相应适用条件；国际指南是方法参考，不替代中国属地规定。未公开取得全文的专业标准，不声称已逐条审查。项目标准、审批与企业采购制度仍需按实际项目核实。

## 二、固定的五层组成

| 层 | 内容 | 选择方式 |
|---|---|---|
| 核心生命周期 C | 启动、范围、设计、采购、施工、调试、验收、接管及项目终点 | 所有基础组合保留相应职责；已完成阶段以证据接续，不重复安排 |
| 行业要求 I | 办公、游戏、金融、生物医药、半导体各自的需求与就绪确认 | 行业选择一项；混合用途可增加其他业务需求，不能自动套第二套总包 |
| 交付采购路径 R | DB 邀请、DB 公开、DBB 邀请、DBB 公开 | 形成 20 套基础组合；每个具体采购包另记采购制度与方式 |
| 专项模块 A | 机房、IT 迁移、声学、动捕、实验室、洁净室等 | 明确需求加载；行业只推荐，不自动确认 |
| 条件转换 X | 毛坯／改造、已租／租前、分期、不停业、设备甲供、现有设施复用 | 调整已选工序与交付接口，不虚构额外工程 |

基础组合适用边界是租户办公及研发设施装修。完整晶圆厂、商业化药品生产线、高等级生物安全设施、独立大型数据中心，不能仅勾一个 Add-on 就宣称覆盖全部项目；应显示“需专项主计划”，本框架只承担已定义的装修和接口部分。

## 三、所有基础组合共用的工序模块

箭头表示成果释放，未表示所有模块全程串行。并行必须写明条件。

| 编号 | 模块及内部工序 | 启动条件 | 完成成果／允许下游开始 | 主责与确认 |
|---|---|---|---|---|
| C01 | 项目授权、目标与责任确认 → PEP／沟通／变更机制 | 业主委托与基本项目资料 | 项目职责及目标记录；启动需求、现场和采购策略工作 | PM 编制，业主确认 |
| C02 | 人员／用途／空间／系统需求 → 现状资料与现场核查 → 范围与复用边界 → 预算及采购包界面 | C01，可与 PEP 并行 | 已确认需求书、范围清单、未知项及责任人 | PM 协调，用户部门／设计／IT／FM 确认 |
| C03 | 方案 → 空间与机电协调 → 发包所需资料 → 分包／分区施工释放设计 | C02；设计责任人已获得有效委任 | TENDER_READY[p] 与 DESIGN_RELEASED[p,z] 分开；发标成熟度不等于施工成熟度 | 相应设计责任方出图，业主按授权确认 |
| C04 | 采购策略与制度判定 → 招采包资料 → 市场选择 → 评审 → 授标与生效条件 | 需求及包边界足够成熟 | CONTRACT_EFFECTIVE[p]；不能把推荐中标直接视为开工授权 | 采购／QS／PM，业主授权人 |
| C05 | 属地与物业适用性核查 → 分事项资料 → 申报／审查／整改 → 取得阶段允许条件 | 场地用途、改造内容等资料；与设计协调并行 | APPROVAL_CLEARANCE[事项,动作,z]，分别控制开工、测试或使用 | 业主及设计／报建责任方；主管机关或物业按事项 |
| C06 | 现场移交 → 保护／隔离／施工方案／临设 → 对应工作面开工条件确认 | 场地交付及该工作面授权、设计、必要批准 | WORKFRONT_RELEASED[z]，无需机械等待其他分区 | GC／PM，业主或场地管理人确认 |
| C07 | 材料样板与深化 → 设备参数批准 → 订货 → 制造／必要厂验 → 物流 → 分设备到货验收 | 对应采购授权与设备技术冻结；甲供责任另记 | EQUIPMENT_RECEIVED[e]，只接使用该设备的安装工序 | 采购责任方、供应商、专业工程师 |
| C08 | 放线与综合协调 → 隐蔽机电／基层 → 检查与必要试验 → 封闭 → 饰面 → 末端设备 → 成品保护／整改 | 每项施工释放、工作面和相关材料条件 | MECHANICAL_COMPLETE[系统,z]；隐蔽放行按墙／顶／地／系统分别记录 | GC 及分包，设计／监理等按合同与适用要求 |
| C09 | 测试方案提前批准 → 安装检查 → 单系统调试 → 接口联调 → 性能验证 → 缺陷关闭／复测 | 安装完成、能源介质可用、测试环境满足 | SYSTEM_ACCEPTED[s,z]；供电可用不等于系统性能已验证 | 专业承包商执行，调试负责人协调，业主代表确认 |
| C10 | 竣工质量与适用专项验收 → 环境／安全／资料核对 → 阻断缺陷关闭 → 区域交付批准 | 各适用系统及要求已满足 | OCCUPANCY_READY[z] 或 FACILITY_HANDOVER[z]；内部放行不命名为政府许可证 | PM 汇总，业主授权人及相关法定责任方 |
| C11 | 运维参与 → 台账／竣工图／手册分批编制 → 培训 → 接管签认 | 从需求设计阶段开始，资料随施工更新 | OPERATIONS_ACCEPTED[z]；基本接管不能随扩展 FM 服务关闭而删除 | GC／供应商提供，业主运维／物业按资产边界接收 |
| C12 | 搬迁／启用策划 → 资产与人员分批方案 → 演练／放行 → 执行 → 业务核验 → 项目终点 | 策划在范围明确后开始；执行等待相应交付及业务条件 | MOVE_COMPLETE 或 SERVICE_START；无需搬迁的项目用移交／启用终点 | 用户部门／IT／搬迁团队，业主业务负责人确认 |
| C13 | 遗留缺陷跟踪 → 结算／保修资料 → 约定后评估或季节性验证 | 交付条件约定允许的非阻断事项 | AFTERCARE_CLOSED；与搬迁目标分开，不把保修期算成搬迁日期 | 合同责任方与业主 |

核心施工约束：不能用一条“所有隐蔽验收”替代不同工作面的检查；封墙／封顶等待对应隐蔽放行。系统测试等待相关系统完成和运行条件，不能仅靠“物理竣工”名称释放。家具、AV、IT 可按区域和安装条件并行；不统一规定全部家具完成才能开始全部 AV。空气检测的标准、对象、采样条件及是否复测按适用要求定义，不默认套两次固定检测。

## 四、四套交付／采购路径

### R01：DB＋邀请

需求与性能目标、发包边界 → 雇主要求／招采文件和候选供应商准备并行 → 包发标条件齐备 → 邀请发出 → 投标准备窗口（踏勘、问答、补遗在窗口内） → 截止提交 → 评审及允许的澄清 → 授标批准 → 合同生效／授权 → D&B 设计协调与分包施工图释放 → 对应施工。

DB 不等于无前期设计。雇主要求、性能标准、设计责任和验收标准必须足以比较方案；投标是否提交概念方案、提交深度如何，写入包规则。中标后设计及设备选择按照获准责任继续深化。普通初设不得自动充当任何报审文件。

### R02：DB＋公开

采用 R01 的设计责任与中标后设计路径；市场选择换为公开公告与相应资格程序。资格预审／后审择一或按适用制度配置，不重复强制。按适用制度安排开标、评标、澄清、公示／异议处理、授标及合同。没有已确认制度依据，不插入多轮降价或 BAFO。

### R03：DBB＋邀请

需求 → 设计服务有效委任（已委任则核验证据，未委任则按设计包策略采购） → 方案／协调设计 → GC 发包图纸、规格、清单及界面达到约定成熟度 → GC 邀请采购 → 授标生效 → 承包商施工深化／材料报审 → 相应施工图及工作面释放 → 施工。

短名单准备与招采文件编制可并行。GC 发标、最终施工图释放和行政批准是不同门；是否可在全部最终图纸完成前发标，必须记录信息成熟度、暂定范围及风险承担。早期发包是明确策略，不是自动降标准。

### R04：DBB＋公开

采用 R03 的设计责任及 GC 包成熟度要求，GC 市场选择换为公开路线及适用程序。设计服务包可以已完成，也可以采用与 GC 不同的合法采购方式；不能把 GC 的公开选择强行复制给设计、家具及 IT 包。

### 四路线共同采购规则

1. 区分 market_method（邀请／公开）、procurement_regime（适用采购制度）、mandatory_tender_status（是否依法必须招标）。未知不得由企业所有制或邀请二字代替判断。
2. 20 套命名采用 GC／D&B 主包方式；设计包、设备包、家具、IT 等记各自方式。未给定的辅助包仅列“委任／采购待定”，不臆造完整公开招标链。
3. 发标门 = 文件达到约定成熟度＋评审标准＋范围界面＋内部发布授权＋适用发布条件。
4. 编标从发标开始；踏勘和答疑按计划在编标窗口内进行。影响编标的补遗是否需要延期按适用规则处理，不能每次答疑后自动重启完整编标工期。
5. 回标截止后才释放评审；评审澄清与商务重新谈判区分。BAFO 仅在已确认允许的采购制度与公布程序下启用；“非必须招标”本身也不等于可自由改变实质条件。
6. 依法必须招标项目的投标准备最低期限需保护，不能因 invite 或面积小而取消。此处定义工序及约束，不设置所有项目统一招采天数。
7. 授标、合同生效、开工授权分开；提前采购／提前开工必须有有效授权与风险承担安排。

法律依据限于：招标投标法第 2、24、39、43 条及实施条例相关规则；详见依据表。用户项目的制度适用性仍为项目输入，不在此推定。

## 五、五个行业要求模块

这些模块是每行业四套的专业差异，分别嵌入 C02、C03、C09～C12。

| 行业 | 需求阶段必做确认 | 设计与交付的行业接口 | 不能默认加载 |
|---|---|---|---|
| I01 办公 | 人数／工位、会议与协作、ITAV、门禁、物业供给与复用、搬迁方式 | 工位与会议功能确认 → 布局和系统界面批准 → 用户功能检查及接管 | 专项数据中心、租前 TDD、额外认证 |
| I02 游戏 | 开发／测试岗位、终端与算力、业务连续性、内容制作与声学需求是否存在 | IT 及研发用户确认性能需求 → 负荷／网络／空间协调 → 选定业务场景验证 | 动捕、录音棚、结构加固、N+1、特定负荷密度 |
| I03 金融 | 普通办公／交易／网点用途、业务关键性、数据／物理安全边界、业务中断容忍度 | 风险与 IT／安防责任人批准要求 → 冗余／分区设计（若需） → 业务可用与接管确认 | 交易大厅、金库、Tier 等级、双路 UPS |
| I04 生物医药 | 办公／湿实验／干实验／生产用途、物料与风险、设备、是否 GxP 或生物安全要求 | 使用方／EHS／质量职责确认 → 选中设施接口及验证策略 → 分别定义场地交付与实验／生产启用 | 洁净等级、负压、环评具体程序、GMP 全验证链 |
| I05 半导体 | IC 设计办公／验证实验／试制／制造用途、设备清单、工艺介质与环境要求 | 设备厂家条件 → 设施能力及接口核对 → 设备接入与业务功能验收 | 特气、UPW、微振基座、洁净室、某一 VC 等级 |

行业要求全部是必须完成的确认工作，但答案可以是“不需要某专项”。不需要的专项不会生成施工任务。确认范围未知时输出基础方案及待决项，不能把它称为包含全部潜在专项的完整计划。

## 六、Add-on 的统一契约

每个模块有：固定编号／版本、适用范围、启用与排除条件、输入证据、工序与阶段、主责、前置成果、内部并行条件、测试验收成果、下游接口、共用工作归属、适用依据、当前支持级别。

专项一旦选入，其必要工作不会再让用户逐项选择是否执行。与已有设施连接时，可由“复用核验合格”替代新建，但不能直接删除需求。

每一工序实例以“模块＋系统／区域＋设备对象”识别，跨模块共用的电源、管线、消防接口只保留一个负责实例，其他模块引用它的成果。工序名称可修改，接口标识保持稳定。

完整目录及每项工序见 02_Addon模块工序与接口.csv；所有条目均为本轮规格设计，不能误称目前代码已支持。

### 两个关键专项的展开示例

**专项机房 A04**：需求与容量／可用性确认 → 场地与能源核查 → 各系统协调设计；设计和采购授权满足后分别采购设备，施工面具备后开展基础／围护；对应设备到货与相关粗装完成后安装 → 安装检查及送电／制冷条件确认 → 单系统与故障工况联调 → 问题闭合 → DC_READY。DC_READY 由 IT 与设施责任人确认供电、制冷、环境、网络、安全及接管边界后释放服务器部署；是否提前于全楼以及提前多少由项目目标确定。结构加固、气体灭火和冗余等级均按设计需要，不统一预设。

**IT 迁移 A05**：系统资产／依赖盘点 → 中断容忍与恢复目标 → 切换／回退方案 → 通信链路与目标环境准备 → 预部署与演练 → go/no-go → 批次迁移／切换 → 业务验证 → 稳定观察与旧环境退出许可。策划在需求明确后开始；预部署等待目标环境就绪，切换等待业务授权与回退条件。没有本次机房新建时，可接受经核验的现有机房／云端就绪接口。数据备份和回退验证不能用总包装修竣工代替。

**实验／洁净／设备**：洁净围护完成不释放实验启用；选定 HVAC、压差、排风处理、介质、安全联锁和环境验证共同形成区域就绪。洁净粒子等级、实验安全等级与 GxP 合规是不同维度，分别判断。空间可交付不等于工艺或生产可启动。

## 七、条件转换与审批

- 毛坯：不加载既有装修拆除；仍核对基层、荷载、机电供给和场地交付缺陷。
- Cat A／既有装修：核对保留范围与改造界面；不把 Cat A 简单等同毛坯。局改按区域和系统定义，不只按拆除比例削减整套工序。
- 拆除：若选中范围需要拆改，插入现状调查、隔离停运、保护、必要批准、拆除与清运、复核交付；必须在对应新建前完成，不能因“Add-on 未勾”跳过。
- 已租场地：保留适当的技术现状核查；租赁决策门只在租前情境启用。
- 分期交付：每区域各有施工、测试、必要审批、系统保障和交付门；共享设施就绪先于依赖它的区域启用。某专项延后是否影响其他区域由隔离与服务边界决定。
- 不停业：插入在用系统调查、保护／隔离、停机窗口批准、临时供给、切换验证；施工日历选 7D 不能替代这些条件。
- 外部甲供／物业工作：保留需方日期、负责人、接口条件与外部完成门，不虚构为总包施工。
- 消防、施工许可、环保等：先判适用路径，再把该事项挂在正确动作前；所有项目有适用性核查，但不强制每项目都有同一行政审批。未知以条件和规划预留展示，不设虚假“已获批”零日门。
- 环保模块区分前期判断／需办程序、配套设施、调试监测与适用验收，不把前期事项全部推到竣工收尾。

## 八、Input／Prompt 判定

详见 03_入口判定与闭环验收_V1.md。统一接收“需要／不需要／待确认／既有复用／他方提供”，空白是待确认，不是假。行业只产生推荐，不提升为已确认输入。

确认工作与实体工作分开：例如“确认是否有实验室”属于行业基础，实验室施工只有需求确认后进入。若未知影响总工期，输出基础情境并明确未覆盖范围，必要时单列可选情境，不能默默删去或默默加上。

## 九、从现状迁移的优先次序

1. 先把 20 个组合改成对核心、行业、路线的引用；独立出项目交付终点。
2. 将原行业强制包改成 Add-on，增加来源、状态及适用范围。
3. 按系统／设备接到货、测试和交付门；修复现有专项断链、关闭 FM 丢终点。
4. 重构 GC 编标窗口与合法评审分支；拆开机房就绪、IT 策划／部署／切换。
5. 同步 intake 和 Prompt 提取规则；移除重复任务与按名字猜接口。
6. 定向验证工序组合和关闭路径；再调整工期，最后跑代表项目和原生 MPP 验证。

这份 V1 明确的是模块规格与专业判断，不是工程项目签收，也不是已实现的能力声明。模块的项目级技术参数仍由已批准设计、业主要求和适用标准提供。

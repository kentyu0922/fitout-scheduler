# 六阶段主表与行业判断（rc11）

本文件是当前对客结构规则，取代旧资料中的九阶段/专项独立L2展示方式。内部工序语义与模块标识继续使用，不按显示标题推断工期或法律适用性。

## 六阶段边界

L1为项目名称；L2采用以下六段；L3为工作包及真实放行节点；招采阶段的L3为采购包，具体工序放L4。阶段可重叠，不串接L2。

| L2 | 归属 | 边界 |
|---|---|---|
| 前期规划 | 用途、岗位设备需求、现场条件、策略与搬迁策划 | 搬迁策划不等于实际搬迁；物业资料获取不等于批准 |
| 设计阶段 | 方案、行业使用条件、接口协调、施工图及技术深化 | 外部图审及许可归报审 |
| 招采阶段 | 设计服务、总包、专项设备及家具采购、生产交货与到货检查 | 保留采购对象，避免两条相同“发出RFP”；安装不放在这里 |
| 报审阶段 | 适用的施工图审查、消防设计审查、物业图审、施工许可 | 技术准备条件不冒充政府批准；竣工手续归最后一段 |
| 施工阶段 | 进场、放线、分阶段实体施工、隐蔽验收、家具及设备安装、单机准备 | 隐蔽验收留在其放行工序附近；综合性能验收归最后一段 |
| 竣工验收阶段 | 系统联调、竣工验收整改、专项性能检测、空气检测、资料培训、入驻放行与搬迁 | 物理竣工、入驻具备、搬迁完成分别保留；不能用L2结束日代替任何一个 |

物业资料获取仍属前期规划；家具到货属招采、安装属施工；IT迁移策划属前期、部署属施工、切换及业务验证属竣工验收。六段是汇报分类，不改变原任务semantic_phase、日历、工期、放行关系。具体匹配集中在core/master_reporting.py。

## 行业基础：有成果、有接口，不强塞设施

五行业的基础工作不只换确认名称：工作包写明岗位/用途核对、设计审查内容、现场检查对象、使用场景与接管成果。定义位于core/industry_base.py及core/module_integration.py，源工作保留在工作包备注。

| 行业 | 需求与设计重点 | 现场与交付重点 |
|---|---|---|
| 通用办公 | 人数席位、会议设施、访客流线与维护空间 | 点位标识、典型办公场景、报修与接管 |
| 游戏 | 开发测试岗位设备、供电散热、协作与安静分区及使用时段 | 回路端口、评审协作及延时使用条件、支持与权限流程 |
| 金融 | 业务岗位、保密分区、资料存放、通信及中断容忍 | 访问边界、角色权限与通信、既有恢复安排和风险移交 |
| 生物医药 | 房间用途、样品物料及实验活动边界、办公设备接口 | 用途变更、入驻物品与允许活动、后续变更流程 |
| 半导体 | 设计工作站与硬件测试边界、负荷散热及设备预留 | 回路端口、代表负载使用验证、设备接口及变更流程 |

这些是行业核对清单，不能把未提供的岗位、设备或活动写成已确认事实。客户明确无需行业特定岗位核对时，可用industry_work_profile=general_office（intake选择“仅通用办公核对”）；保留项目行业，基础五阶段改用通用办公工作成果。该选项不取消已选择的addon；明确的专项需求与接口照常保留。留空或sector_review沿用行业核对。不得仅凭“纯办公室”自行关闭行业核对。相同纯办公室实体施工可以相同；不得宣称五套完全不同的施工拓扑。

设计工作约束施工图、现场点位核查接隐蔽验收、使用验证接入驻放行。每个工作包带输入任务、成果、验收依据、放行接口。现有完整范围分界、统一安装包、scope_allocation及owner_module继续保留；责任显示三列空白不影响这些规则。

## Prompt 与 intake 同一判断

不增加第二套需求开关。Prompt由agent提取项目事实及原话依据至现有addon_a01…addon_a22；intake使用同名选择，汇入core/project_input.py和core/module_catalog.py。不要用关键词扫描代替理解。

1. 用户明确委托建设/改造某专项：required。明确不需要：excluded。
2. 既有拟复用：existing_claimed；他方提供：provided_by_others。保留条件核验和交接接口，不重复排本项目安装。
3. 未说明：unknown；行业推荐不等于需要。只问会改变范围、放行或关键接口的缺口，已有答案不再问。
4. 新增需求与排除冲突：澄清提供方或范围，不以排除选项悄悄删除必要条件。仅修改一方文字不能解决冲突。
5. 高密负荷不自动推出外电增容；实验活动不自动推出洁净/GMP；金融不自动推出双电双网。逐项核对性能、设备清单、现状余量及合同范围。
6. 确认供电需要增容（external_power_status=upgrade_needed）时，未选状态自动加载A03；明确排除则阻断；他方提供/既有拟复用仍保留外部接口。旧has_server_room、laboratory、it_migration、prelease_tdd字段沿用已有映射与冲突校验。

22项触发含义统一维护在core/scope_selection.py的TRIGGERS，intake选项说明与运行selection_decisions引用同一来源。选择是否可取消取决于原需求：建议项可取消；已确认需求必需的设施应同步撤销需求或明确替代供给。模型不能自行批准替代方案。

## 精简与验证

core/master_completion.py只吸收已被单一行业工作包完成所包含的零天需求/使用验证/接管确认。要求同日历、无约束日期、无时滞FS条件，且其余前置已包含在工作包祖先链内。独立批准、隐蔽验收、设计放行、多系统放行保留。完成依据及原ID保留在completion_conditions和源工序追溯中。不能隐藏正工期任务伪装精简。

日期校验分开处理：展示重分不改任何真实依赖；确认合并仅将消费者连接到代表工作包。应比对原输入日期、映射后的依赖、全部工序覆盖、专项出口能否到达入驻，并对延迟传播做测试。不要为每次示例运行完整历史测试集。

rc9修订：取消默认通风散味独立任务及固定等待（原35天、45天等档位不再自动加载）。最终空气检测连接家具与影音安装完成，采样条件待项目核实；仅明确天数和依据的项目要求可建立特殊窗口。其他工期未校准。rc10已接入上海声明分类的报审分支，其他城市或超出范围仍须核实，详见[工序接口](process_closure.md)。

rc10另将重复行业现场确认并入同次隐蔽验收，实际核对工作及行业检查内容仍保留。该调整位于core/process_closure.py，属于实际接口修订，不能复用旧版日期不变结论。


rc11：招采默认仅设计/施工；家具招采可选，生产供货、接收及安装不归招采。家具工作面移交独立于最终保洁。阶段归属与实际依赖同时检查。

# 当前边界裁定（rc11）

本轮修正汇报层级及范围边界，未完成全部工序的专业审定。边界定义正确、排程可计算、工序专业完整是三项不同判断。程序测试通过不能替代后者。

## 层级边界

L1项目，L2六阶段不变。招采下L3为设计服务招采、施工总包招采，子项L4；DB改用设计施工总包招采。每个包连续显示，包内按开始日期及依赖排序，不把不同包穿插。其他阶段不强制增加层级。

L3汇总日期来自子项，不设自己的工期和前置。实际依赖仍接具体执行工序。子项不重复采购对象前缀。家具及其他专项供货出现时，按供货流展示，不能据此断言已独立发包；“其他设备与专项供货”是待项目拆分的汇报集合，不是一个合同。

## 四类边界不能混用

| 对象 | 表达的内容 | 不代表什么 |
|---|---|---|
| 行业基础 | 需求、设计、现场核查、使用验证及接管的核对内容 | 不是自动增加物理设施，也不是一个承包合同 |
| addon | 已确认的专项工程/服务范围或待核验外部接口 | 不一定独立招标；不同addon可能同一合同 |
| 采购包 | 由一次委托/合同覆盖的采购范围 | 不自动覆盖该专业所有设计、安装、调试责任 |
| L3/L4工作包 | 可汇报、具有完成成果及真实交接条件的工作 | 不是承包商身份或批准已完成的证明 |

工程范围与合同范围通过项目发包策略、设备清单、空间界面和供货安装分工确认。责任列留白不会取消scope_allocation、owner_module和统一安装规则。既有拟复用/他方提供不能当作已验收；排除本项目安装也不能删除实际需要的外部条件。

## 六阶段边界与出口

| 阶段 | 包含 | 出口 / 下游条件 |
|---|---|---|
| 前期规划 | 用途、需求、现状与容量、策略、搬迁策划 | 形成可供设计和采购采用的需求及已知限制，不代表设计已完成 |
| 设计阶段 | 方案、专业设计、范围及接口协调、施工图 | 已批准的相应版本；发标图、施工图、设备深化图应区分，不默认一张“图纸确认”释放全部工作 |
| 招采阶段 | 设计/总包委托、供货选择、下单、生产交货及到货检查 | 设计合同释放设计；施工合同结合适用许可及工作面释放进场；到货结合现场条件释放安装 |
| 报审阶段 | 适用的开工前外部图审、物业图审及许可 | 对相应工作放行，不等同内部技术审查；待确认适用性不写成已批准 |
| 施工阶段 | 放线、粗装、隐蔽检查、封闭收口、家具/设备安装、单机条件准备 | 分系统安装及检查记录；隐蔽放行先于其遮盖工序，不要求所有专业同时完成 |
| 竣工验收阶段 | 综合调试、相关验收整改、检测、最终资料和培训、接管及搬迁 | 区分装修机电完成、入驻条件具备、搬迁完成；不能用阶段结束日替代控制点 |

资料编制、培训准备可以早于最终交付，但资料正式移交、实际演练和运行接管需要各自条件。后续工序修订必须体现这个区别，不能为了阶段整齐强制串行。
